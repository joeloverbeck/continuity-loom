## Breakdown decisions

- **Structural: why `record` and `compiler` are separate slices.** The cut is drawn between storage
  and compilation because a half-migrated store would otherwise be observable. #201 lands the whole
  stored shape as one coherent state — round-trip, schema, migration of older projects, and export —
  and #202 only reads it. There is no intermediate state in which the prose prompt already depends on
  the new field while some projects have not been migrated to carry it.
- **Dependency: `#188` gates `compiler` only.** #188 is a pre-existing tracker prerequisite, not a
  product of this breakdown, and it constrains compilation alone. #201 does not inherit it and may
  start immediately. #203 lists only #202 as its blocker; #201 and #188 reach it transitively through
  #202 and are deliberately not restated there.
- **Story coverage: durable in the child bodies, not duplicated here.** US1, US2, and US3 each map to
  exactly one child under that child's `## User stories covered` section (US1 → #201, US2 → #202,
  US3 → #203). The mapping is authoritative there; this ledger intentionally does not repeat it, so
  there is only one place to correct if a story is re-scoped.
- **Checklist: only `editor` is browser-visible.** #203 maps all eight canonical browser-visible
  guidance items one-for-one onto its eight acceptance criteria. #201 and #202 change no UI, so each
  takes the single specific N/A recorded above rather than an item-by-item mapping.
- **Rationale placement.** These decisions live in this parent ledger rather than in a
  `## Breakdown decisions` note inside the first child, so the structural and dependency reasoning
  stays in one durable place for anyone picking up any of the three slices.
